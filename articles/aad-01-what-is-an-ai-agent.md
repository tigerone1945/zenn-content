# AIエージェントは作れる。でも、設計できていますか？

AIエージェントは、Difyを使えば数十分で作れる時代になりました。

Claude CodeやCodexを使えば、Pythonコードも簡単に生成できます。

しかし、実際に業務へ導入すると、

- 思ったように判断しない
- 担当部署が毎回変わる
- 人へ引き継ぐタイミングが曖昧
- 担当者ごとに動作が変わる

という問題に直面します。

多くの人は、

- プロンプトを書き直す
- LLMを変更する
- RAGを調整する

といった改善を試みます。

しかし、本当の原因はそこではありません。

**AIに何を判断させ、どのような条件で動かすのかが設計されていないこと**です。

AIエージェントは「作る」だけでは価値を生みません。

**正しく設計されて初めて、業務で使えるAIエージェントになります。**

---

# AIエージェント設計とは何か

AIエージェント設計とは、

「どのLLMを使うか」を決めることではありません。

また、

「Difyでどのノードを配置するか」

「Pythonでどう実装するか」

を考えることでもありません。

最初に考えるべきなのは、

- 何を入力として受け取るのか
- AIは何を判断するのか
- 何を出力するのか
- どのような場合に人へ引き継ぐのか

という**業務ルール**です。

この業務ルールをシステムとして表現したものが、

**System Specification**です。

つまり、

**AIエージェント設計を学ぶための方法がSystem Specification**なのです。

# このシリーズで学ぶこと

本シリーズでは、

AIエージェントの作り方ではなく、

**AIエージェントの設計方法**を学びます。

毎回、実際の業務を題材に、

1. As-Is
2. To-Be
3. Business Specification
4. System Specification
5. レビュー
6. 改善後の仕様

という流れで設計を見直していきます。

AIエージェントをレビューしながら、「なぜその仕様が必要なのか」を理解することが目的です。

---

# なぜSystem Specificationなのか

AIモデルは進化し続けています。

利用するフレームワークも変わります。

しかし、

企業の業務ルールや判断基準は簡単には変わりません。

だからこそ、

企業の資産となるのは、

- プロンプト
- 利用するLLM

ではなく、

**System Specification**です。

設計がしっかりしていれば、

Difyでも、

Pythonでも、

Amazon Bedrockでも、

Vertex AIでも、

同じ考え方で実装できます。

# まとめ

AIエージェントの品質は、

モデルだけでは決まりません。

**どのようなSystem Specificationを書くか**が品質を左右します。

そして、System Specificationは目的ではありません。

**AIエージェントを設計するための方法**です。

このシリーズでは、実際のAIエージェントをレビューしながら、業務で使えるAIエージェントを設計する力を身につけていきます。
