# FAQ AIが正しく回答できない理由

「社内FAQをRAGへ登録したのに、期待した回答が返ってこない。」

そんな経験はないでしょうか。

このような場合、多くの人は

- Embeddingモデルを変える
- Chunkサイズを調整する
- LLMを変更する

といった改善を試します。

しかし、原因はRAGそのものではないことも少なくありません。

**FAQ AIが「いつ回答し、いつ回答しないのか」が仕様として定義されていないこと**です。

今回はFAQ AIを例に、

System Specificationをレビューしながら品質を改善していきます。

---

# レビュー前のSystem Specification

まずは次のような仕様を考えます。

```
Input
 ↓
FAQ検索
 ↓
回答生成
 ↓
回答
```

一見すると問題なさそうです。

しかし、この仕様のままでは業務で使えるFAQ AIにはなりません。

---

# レビュー① 検索結果をどう評価するか

検索結果が

- 0件
- 1件
- 20件

だった場合、

同じように回答してよいのでしょうか。

仕様には何も書かれていません。

改善として、

検索結果に対して

- 件数
- 類似度
- スコア

を評価する処理を追加します。

---

# レビュー② AIはいつ回答するのか

検索結果が見つかったからといって、

必ず回答してよいとは限りません。

例えば、

```
Confidence

80%以上

↓

AIが回答

80%未満

↓

担当者へ引き継ぐ
```

という判断基準を定義します。

AIが回答する条件を明確にすることで、

誤回答を減らすことができます。

---

# レビュー③ AIはいつ回答しないのか

AIエージェントは、

答えることだけが仕事ではありません。

「答えない」

という判断も重要です。

例えば、

```
FAQなし

↓

担当者へ転送
```

というルールを追加します。

さらに、

- 就業規則にない内容
- 推測が必要な内容
- Confidenceが低い内容

も人へ引き継ぐ対象として定義します。

---

# 改善後のSystem Specification

レビュー後の仕様は次のようになります。

```
Input
 ↓
質問分類
 ↓
FAQ検索
 ↓
検索結果評価
 ↓
Confidence判定
 ├─80%以上 → AIが回答
 └─80%未満 → 担当者へ転送
```

AIは

「回答する」

だけではなく、

「回答しない」

という判断まで仕様化されました。

---

# 実装技術は後から選べる

ここまで仕様が整理できれば、

実装方法は問いません。

- Dify
- Python
- Amazon Bedrock
- Vertex AI
- Azure AI Foundry

どの技術を採用しても、

同じSystem Specificationを利用できます。

重要なのは、

RAGのチューニングではなく、

**AIの判断基準をレビューすること**です。

---

# レビューチェックリスト

FAQ AIでは次の点を確認します。

- Inputは十分か
- 検索結果を評価しているか
- AIが回答する条件はあるか
- AIが回答しない条件はあるか
- 人へ引き継ぐ条件はあるか
- Confidenceなどの判断基準は定義されているか

---

# まとめ

FAQ AIの品質は、

EmbeddingモデルやLLMだけでは決まりません。

重要なのは、

**AIが「いつ回答し」「いつ人へ引き継ぐか」を仕様として定義すること**です。

RAGを改善する前に、

まずSystem Specificationをレビューしてみてください。
